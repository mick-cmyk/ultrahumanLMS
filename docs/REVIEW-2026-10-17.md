## Headline

The product logic is in good shape. The spec's two protected pieces (`user_matches_rule`, unique-seconds watch tracking) are implemented the way the spec says. The problems are at the edges: one hole that lets a learner fake completion, one that lets a manager overwrite other people's accounts, and brand details baked in as constants and Tailwind classes.

Brand coupling is shallower than feared: "P1xel Forge" appears in about 8 places. The real cost is colour, which is hardcoded as Tailwind grays and greens across 21 files, and the magic-link email, which lives in Supabase Auth and not in the app.

## Must fix

### M1. A learner can write their own progress directly, skipping the video and quiz  [Certain, tested on the live DB]

`20260713100000_initial_schema.sql` grants `select, insert, update, delete` on all tables to `authenticated`. `20260713100300_rls_policies.sql` then adds `lesson_progress_insert_own` and `lesson_progress_update_own` with no column limits. Any logged-in learner can call the REST API directly and set `watch_pct = 1`, `watched_at`, `quiz_score = 1`, `quiz_passed_at`. No trigger guards the table. The comment says "the app writes via record_watch_progress", but the direct path is open.

Effect: "Completed" can be faked with one request. It does not create a re-test, so that person would show as completed and never retention-verified. That inflates the exact headline number your client reads, and it undermines "completed means something".

Fix (new migration): drop both write policies, `revoke insert, update, delete on public.lesson_progress from authenticated`. `record_watch_progress` and `record_quiz_attempt` are `security definer`, so the app keeps working. Add a pgTAP test that an authenticated learner cannot update their own row directly.

Tested: as `ava.jb.south@example.com` (learner), a direct insert into `lesson_progress` with `watch_pct = 1`, `watched_at`, `quiz_score = 1` and `quiz_passed_at` succeeded.

### M2. A manager can overwrite any existing account by "adding" its email  [Certain]

`lib/provision.ts`: if the email already exists, it updates `full_name`, `org_id`, `store_id`, sets `role = 'learner'` and `active = true`, with no check on who owns that account. Both `/api/staff` (add) and `/api/people/import` (manager path) call it with the manager's own org and store.

Effect: a manager who adds an admin's or coordinator's email demotes them to learner, moves them into the manager's store and reactivates them if deactivated. Same for a person in another retailer.

Fix: in `provisionUser`, when the user already exists, a manager call may only proceed if the existing profile has no org yet, or is already in the manager's store. Never change `role` on an existing user from the manager paths. Admin paths can keep the upsert.

Related, same file set: `/api/staff` scope check is `target.org_id === profile.org_id`. If a manager ever has `org_id = null`, that is `null === null` for every admin and coordinator. Require `profile.org_id` to be non-null for managers.

### M3. Open redirect after login  [Certain]

`/auth/callback` and `/auth/confirm` do `new URL(next, origin)` with `next` straight from the query string. `next=//evil.example` resolves to another site. Someone with a valid login link can be bounced off-site after a successful login, which is a good phishing setup.

Fix: accept `next` only if it starts with a single `/` and not `//` or `/\`; otherwise use `/`.

### M4. Both cron functions fail open if `CRON_SECRET` is unset  [Certain]

`retest-dispatch` and `weekly-digest` are deployed with `verify_jwt = false` (so pg_net can call them), and the secret check is `if (CRON_SECRET) { ... }`. If the secret is not set in production, anyone on the internet can trigger a send run. The Resend idempotency key limits duplicate re-tests, but the weekly digest has no such protection.

Fix: if `CRON_SECRET` is missing, return 500 and do nothing. Add it to the go-live checklist as a hard gate.

### M5. Any logged-in user can read manager and admin contact details and other people's scope  [Certain, tested on the live DB]

The live database lets `authenticated` execute functions the repo says are service-role only:

- `digest_recipients()` returned 4 rows (every active manager and admin: id, email, name, role) to a learner.
- `users_in_scope_of(p_viewer uuid)` takes any viewer id with no check that it matches `auth.uid()`. Called with the admin's id, a learner got 23 rows (email, name, org, store for everyone). Needs the admin's uuid, which a learner cannot list today, so practical exploitability is low, but it is an insecure direct object reference by design. `report_summary_for(p_viewer uuid)` has the same flaw.
- `build_retest`, `grade_retest`, `schedule_retest_dispatch`, `schedule_weekly_digest` are also executable by `authenticated`. The token functions need a 256-bit token so they are low risk. The two `schedule_*` functions are not: a learner can call them, and `schedule_retest_dispatch` unschedules the job first and only reschedules if `app.settings.retest_dispatch_url` is set. With that setting missing, one call from any learner switches the re-test cron off.

Fix (new migration): revoke execute on `digest_recipients`, `users_in_scope_of`, `report_summary_for`, `build_retest`, `grade_retest`, `schedule_retest_dispatch`, `schedule_weekly_digest` from `authenticated` (grant to `service_role` only). Better, have the viewer-taking functions ignore the parameter and use `auth.uid()`.

### M6. The repo and the live database have drifted apart  [Certain]

Live has 13 migrations stamped `20260919...` with different names (for example `restrict_function_execute_to_authenticated`, `cron_schedulers`, `org_branding_and_lesson_media`). The repo has 15 files stamped `20260713...`. The repo's function lockdown says token and cron functions are service-role only; the live one grants them to `authenticated`. So what was tested here is not what `supabase db push` would build in Sydney.

Fix: pick one source of truth. Recommended: make the repo authoritative, fix M1 and M5 in new migration files, build a fresh Sydney project from the repo alone, and run the pgTAP suite and a seed-learner smoke test against it. Do not promote this Tokyo project.

## Should fix

### S1. Re-test emails arrive after the shift  [Certain on the cron, Likely on the effect]

The daily cron is `0 8 * * *`, which pg_cron runs in UTC. That is 6pm AEST / 7pm AEDT. The retest email is the product's key touchpoint and it lands after close. Weekly digest `0 9 * * 1` is Monday 7pm/8pm.

Fix: schedule in UTC for roughly 8 to 9am Sydney (`0 22 * * *` gives 8am AEST and 9am AEDT). Better still, make the send hour a per-brand setting.

### S2. Visible bug in the expired re-test message  [Certain]

`app/retest/[token]/page.tsx`: `'This re-test link has expired. You&apos;ll get a fresh one soon.'` is a JS string, so staff will see the literal text `You&apos;ll`. Use a plain apostrophe. Also check the claim: does anything actually send a fresh link on expiry? A requeued test does, but an expired token on a `sent` re-test only gets a reminder if one is still due. Reword or make it true.

### S3. The no-login re-test result links into a login wall  [Certain]

The "Topics to refresh" links go to `/lessons/<id>`, which needs a session. A phone user who arrived by email link with no session hits the login page right when they are motivated to re-learn. Options: send them to `/login` with a sentence that says so, or issue a short-lived session from the token. First is cheap; second is nicer but touches auth, so check with Mick.

### S4. `provisionUser` finds existing users with `listUsers({ perPage: 1000 })`  [Certain]

Past 1000 auth users, an existing person is not found and the import throws "could not locate existing auth user". It also loads 1000 users to find one. Look the email up in `public.users` (already mirrored) instead.

### S5. Accessibility  [Certain unless noted]

- Bunny `<iframe>` has no `title`. Fails WCAG 4.1.2.
- Quiz and re-test results have no `aria-live` region and no focus move after submit. A screen reader user gets no announcement that marking finished.
- Progress bars are plain divs with no `role="progressbar"` or value.
- Sample `<video>` has no `<track>` captions. Real Bunny videos need captions turned on too. Retail floors are loud, so captions help everyone, not only compliance.
- `BrandBand` puts white text on whatever `brand_color` is. JB's `#FFE600` would fail contrast badly. The email renderer already has a `textOn()` helper for this; reuse it in the app.
- `text-gray-400` (6 uses) on white is about 2.8:1 and fails AA. `text-gray-500` passes at about 4.8:1 but only just.
- Answer radios are the browser default size. The label has padding so the tap target is OK, but make the whole row at least 44px high.
- The Submit button is disabled with no explanation until every question is answered. Add one line: "Answer all questions to submit."
- No skip link (low value on this layout).

### S6. The reporting gap does not jump out  [Certain]

`app/reports/page.tsx` shows Completed and Retention-verified as two independent bars. The story is the difference. Add a third number: "of those who completed, X% still knew it a week later", and call out the count of people who completed but have not been verified. Make that the lead figure for managers and coordinators. The spec also lists views by org, state, store and person; the course drill-down groups some of these, but I did not confirm each is present.

### S7. Lock down new database functions by default, not by re-running a loop  [Certain]

`20260713101400_restrict_function_execute.sql` fixes functions that exist today. Any function added later is executable by `anon` again until someone remembers. Add `alter default privileges in schema public revoke execute on functions from public, anon;` so it is automatic, and keep the loop for the service-role-only list.

### S8. Wording and voice  [Certain]

- 48 em dashes across UI and email copy. Mick's house style is none.
- "Re-test" in the UI, "quick check" in the email. Pick one word and use it everywhere.
- "G'day" is hardcoded on the home page. Fine for Kenshu, wrong for some brands. This is voice config (see brand design).
- Email subject: "Quick 2-minute check on X, no login needed" is good. The reminder subject is fine. The weekly digest was not reviewed in detail.
- The retest-dispatch file says `RETEST_QUESTION_HINT = 4` while the email says "4-question check". If the sample size changes, the email lies. Read it from one constant.

### S9. Two magic-link templates that disagree  [Certain]

`supabase/templates/magic_link.html` uses `{{ .SiteURL }}/auth/confirm?token_hash=...` (works in any browser). `magic_link_hosted.html` uses `{{ .ConfirmationURL }}` (PKCE, same browser only, hence the `/auth/callback` route and the hash-fragment handling on the login page). `config.toml` templates only apply to local Supabase. The hosted template is pasted into the dashboard by hand. Decide on one flow, generate the template from brand config, and note in the go-live list that hosted templates are not deployed by migrations.

PKCE same-browser matters here: staff who request the link on a shared floor PC and open it on their phone will fail. The `token_hash` flow avoids this. Recommend `token_hash` for hosted too.

## Multi-brand design: Kenshu now, UltraHuman next

Requirement as given: colours, name, links, branding, voice, and the connectors (Supabase, Resend) must all be swappable per brand.

### Decision: one codebase, one deployment per brand

Recommendation: a single repo with a brand config, deployed once per brand. Each brand gets its own Vercel project, its own Supabase project, its own Resend domain and its own Bunny library or collection.

Why not one shared deployment that picks the brand from the hostname:
- You asked for the Supabase and Resend connectors to be changeable per brand. A shared deployment has one database and one auth project, so it cannot do that. Separate projects can.
- A different company's staff data in the same database as NARTA's is a conversation with UltraHuman's legal team you do not need to have. Separate projects make "your data is only yours" a one-line answer.
- It does not need the hostname-resolution layer I earlier said to park. That earlier advice assumed one pilot. With a second brand named, it changes: brand config is now in scope, but hostname routing on a shared DB is still not what you asked for.

Costs of this choice, stated honestly:
- Each brand is a Supabase Pro project (about USD 25 a month) plus its own migration run and edge-function deploy. A schema change means applying it N times. Mitigate with one `scripts/deploy-brand.ts` that runs migrations and deploys functions for a named brand.
- You lose a single cross-brand view. That is fine until someone asks for one.

Door left open: write `getBrand()` as a function, not a constant. Today it reads the `BRAND` environment variable. If you later want true multi-tenant on one deployment, the same function can resolve from the request hostname. No other code changes.

### What "a brand" is

One typed object, one file per brand: `brands/kenshu.ts`, `brands/ultrahuman.ts`. Public, non-secret values only.

```
identity   name, shortName, legalName, productName, tagline
urls       appUrl, marketingUrl, supportEmail, privacyUrl, termsUrl
theme      primary, onPrimary, accent, ink, muted, surface, line,
           radius, fontFamily, logoLight, logoDark, favicon
voice      locale, greeting(name), retestNoun ("quick check"),
           loginHeading, loginBody, emptyState, sign-off,
           email.{ retestSubject, retestBody, reminderBody, digestIntro, footer }
email      fromName, fromAddress, replyTo, sendHourLocal, timezone
learning   retestDelayDays, requeueDelayDays, maxCycles, passMark,
           watchThreshold, questionCount     (replaces lib/constants.ts values)
features   flags for anything brand specific
```

Secrets and connector addresses stay in environment variables per deployment, never in the brand file:

```
NEXT_PUBLIC_SUPABASE_URL, NEXT_PUBLIC_SUPABASE_ANON_KEY, SUPABASE_SERVICE_ROLE_KEY
RESEND_API_KEY, CRON_SECRET
BUNNY_STREAM_LIBRARY_ID, BUNNY_STREAM_EMBED_TOKEN_KEY
BRAND=kenshu
```

Layering to keep: platform brand (Kenshu or UltraHuman) is the outer layer. The existing per-org brand (`orgs.brand_color`, `orgs.logo_url`, for example JB Hi-Fi inside Kenshu) stays as an inner layer for the dashboard band and the email header.

### The magic-link email, specifically

This is the part that is easy to get wrong. Supabase sends the login email, not your app, so its template and sender are per Supabase project. With one project per brand that is fine: each project gets its own SMTP (Resend) settings and its own template. To stop the HTML drifting, add a small script that renders the magic-link template from the brand file and prints it for pasting, or pushes it with `supabase config push`. That also fixes S9.

The alternative, a Supabase Send Email Hook that calls your own endpoint and sends through Resend with the brand resolved at send time, is only needed if you go multi-tenant on one Supabase project. Not needed for this plan.
